# Maintenance API

Maintenance API — REST API для управления оборудованием и заявками на техническое обслуживание оборудования. Проект реализован на Node.js, TypeScript и Express. Данные на текущем этапе хранятся в JSON и доступны через repository layer, что позволяет в дальнейшем заменить хранилище на базу данных без изменения основной бизнес-логики.

API предоставляет возможность создавать, получать, изменять и удалять оборудование, а также создавать и управлять заявками на техническое обслуживание. Для оборудования поддерживаются типы `turbine`, `inverter`, `sensor` и `substation`, а статусы оборудования включают `operational`, `maintenance`, `fault` и `decommissioned`. Каждое оборудование имеет уникальный UUID, название, серийный номер, координаты, статус и дату установки.

Для заявок на техническое обслуживание поддерживаются приоритеты `low`, `medium`, `high` и `critical`. Статусы заявок: `new`, `in_progress`, `done` и `rejected`. Переходы между статусами контролируются бизнес-логикой: `new` может перейти в `in_progress` или `rejected`, а `in_progress` может перейти в `done` или `rejected`. После перехода в `done` или `rejected` дальнейшее изменение статуса запрещено. Недопустимый переход возвращает ошибку `409 Conflict`.

Основной API доступен по адресу `http://localhost:5000/api`. Для проверки работоспособности сервера используется `GET /api/health`. Для работы с оборудованием доступны следующие endpoints: `GET /api/equipment` для получения списка, `POST /api/equipment` для создания, `GET /api/equipment/:id` для получения конкретного оборудования, `PATCH /api/equipment/:id` для изменения, `DELETE /api/equipment/:id` для удаления и `GET /api/equipment/:id/weather` для получения погодного прогноза по координатам оборудования. Также доступен `GET /api/equipment/:id/requests` для получения заявок конкретного оборудования.

Для работы с заявками доступны `GET /api/requests`, `POST /api/requests`, `GET /api/requests/:id`, `PATCH /api/requests/:id`, `PATCH /api/requests/:id/status` и `DELETE /api/requests/:id`. При создании заявки сервер самостоятельно устанавливает UUID, начальный статус `new`, а также поля `createdAt` и `updatedAt`.

Списки оборудования и заявок поддерживают фильтрацию, сортировку и пагинацию. Для оборудования можно использовать фильтры по `type` и `status`, сортировку по `name`, `type`, `status` и `installedAt`, а также параметры `page` и `limit`. Для заявок доступны фильтры по `priority`, `status`, `equipmentId`, `plannedFrom` и `plannedTo`, сортировка по `title`, `priority`, `status` и `plannedAt`, а также пагинация. Ответы списков содержат данные и мета-информацию с общим количеством элементов, текущей страницей и лимитом.

API содержит валидацию входных данных. Проверяются обязательные поля, допустимые значения enum-полей, длина строк, корректность дат, координаты, существование оборудования при создании заявки и уникальность серийного номера оборудования. Серверные поля, такие как `id`, `createdAt` и `updatedAt`, не должны изменяться клиентом. Неизвестные поля запроса не используются в бизнес-логике.

Для получения прогноза погоды используется внешний сервис Open-Meteo. Endpoint `GET /api/equipment/:id/weather` использует координаты оборудования и возвращает прогноз с датой, минимальной и максимальной температурой и количеством осадков. Запрос к внешнему сервису выполняется с использованием timeout, заданного через переменную окружения `REQUEST_TIMEOUT_MS`.

В проекте используется слоистая архитектура `routes → controllers → services → repositories → data`. Routes отвечают за определение HTTP endpoints, controllers обрабатывают HTTP-запросы и ответы, services содержат бизнес-логику, repositories отвечают за доступ к данным, а data содержит текущее JSON-хранилище. Такой подход позволяет отделить бизнес-логику от HTTP-слоя и слоя хранения данных.

Ошибки обрабатываются централизованным middleware. API использует единый формат ошибок:

`{ "error": { "code": "...", "message": "...", "details": [], "requestId": "..." } }`

Для различных ситуаций используются соответствующие HTTP-коды: `400` для ошибок валидации, `404` для отсутствующих ресурсов, `409` для конфликтов бизнес-логики, `429` при превышении rate limit, `502` при ошибках внешнего weather API, `504` при timeout внешнего сервиса и `500` для непредвиденных ошибок сервера.

Для безопасности используются Helmet, CORS с явно заданными разрешёнными origins, rate limiting и ограничение размера JSON body. По умолчанию размер JSON-запроса ограничен 100 KB. Конфигурация приложения хранится в переменных окружения и не должна содержать секреты в репозитории.

Каждому HTTP-запросу сервер присваивает уникальный `X-Request-Id`. Этот идентификатор также используется в ошибках API и логах, что позволяет связать клиентский запрос с серверной записью. В логах фиксируются уровень сообщения, request ID, HTTP method, путь, статус ответа и продолжительность выполнения запроса.

Для запуска проекта необходимо установить зависимости командой `npm install`, создать `.env` на основе `.env.example` и указать необходимые переменные окружения. Основные переменные включают `PORT`, `NODE_ENV`, `CORS_ORIGINS`, `RATE_LIMIT_WINDOW_MS`, `RATE_LIMIT_MAX`, `WEATHER_API_URL` и `REQUEST_TIMEOUT_MS`.

Для запуска проекта в режиме разработки используется `npm run dev`. Для проверки TypeScript-сборки используется `npm run build`. После сборки приложение запускается командой `npm start`.

Пример конфигурации `.env`:

`PORT=5000`

`NODE_ENV=development`

`CORS_ORIGINS=http://localhost:3000`

`RATE_LIMIT_WINDOW_MS=900000`

`RATE_LIMIT_MAX=100`

`WEATHER_API_URL=https://api.open-meteo.com/v1/forecast`

`REQUEST_TIMEOUT_MS=5000`

API можно тестировать с помощью curl или Postman. Основные сценарии тестирования включают проверку health endpoint, CRUD операций оборудования, CRUD операций заявок, status transitions, фильтрации, сортировки, пагинации, погодного endpoint, ошибок валидации, duplicate serial number, отсутствующих ресурсов, удаления оборудования с открытыми заявками, rate limiting, request ID и обработки ошибок внешнего weather API.

Проект использует Git feature-branch workflow. Новые изменения выполняются в отдельных ветках, после чего создаётся Pull Request в `main`. После успешного merge локальная ветка `main` обновляется через `git pull origin main`.

Текущая версия проекта содержит REST API для оборудования и maintenance requests, валидацию, бизнес-логику переходов статусов, фильтрацию, сортировку, пагинацию, интеграцию с Open-Meteo, централизованную обработку ошибок, CORS, Helmet, rate limiting, request ID, logging и конфигурацию через environment variables.
